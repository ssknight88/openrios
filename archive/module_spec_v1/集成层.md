# 集成层

本层负责子模块之间，**不重复任何子模块内部的定义**。三件事：接线拓扑、胶水逻辑、协议编排。

术语：**库内**指本目录下有微架构文档的模块；**库外**指 FE、各 FU（含 G3 的 LSU）、
`g3_lsu_iface`、顶层。库外对端没有文档，凡送往库外的边，其传输语义由本层补齐。

---

## 1. 接线拓扑

只做连接，不做决定，**不产生新字段**。行式：`源.端口 → 目的.端口：字段`。
传输语义由**消费方**的 in-event 登记，本层不重复；**送往库外的边例外**，在 §1.5 单列。

### 1.5 库外边的传输语义

库外对端无文档，无人登记，故在此补：

```text
IB                     → FE                accepted_slot            触发（回压指示，未接受的
                                                                    候选 FE 须保持重发）
IB                     → FE                room_q                   broadcast（Static Info，
                                                                    容量提示，FE 当拍用掉）
ISQ_Group_g            → 组内 FU           issue payload            move（FU 锁进自己的流水寄存器）
p3_arbiter_G0/G1       → 组内各 FU         winner_grant / loser_hold 触发（单线指示）
flush_model            → FE                redirect_*               move（FE 据此重置取指 PC）
flush_model            → 各 FU / g3_lsu_iface  global_flush_late    触发（单线脉冲）
commit_unit            → g3_lsu_iface      store_drain_tag          地址（寻址 tag）
csr_control            → G0 的 CSR FU      CSR[csr_addr]            broadcast（当拍读，不留存）
```

### 1.6 连接的合法性约束

- **demux**：同一起点的 event 无交集
- **fan-out**：单向非握手
- **mux**：同一终点的 event 无交集

本设计中需逐条核的：`Buffer` 的 4 个 writeback 写口地址正交（四条 P3 lane 属四个不同在飞 tag）；
`CompletionScoreboard` 同理；`INT_DST_REG` 的 2 个 alloc 写口同格时按 §3.4 的写口次序解决。

### 1.7 对账记录

模块文档按新规范重写后，与本层边表做过两轮对账，共查出 7 处不一致，**现已全部修正**。
留此记录是为了标明**每处的责任方**——本层是验证模块文档的工具，
工具自己的错与被测对象的错必须分开算。

**A. 本层漏登记的边（5 条，责任在本层）**——模块 ⑥ 已声明，本层无边供给：

```text
FE          → IB            fe_valid[1:0]        enqueue 的两位前缀握手要它，
                                                 §1.1 原先只登记了 IB_Payload
IB          → FE            room_q               IB 的 Static Info，消费者是 FE 的提前节流。
                                                 不登记则会被消费者核对误判为死字段
G0 的 CSR FU → csr_control   csr_addr（读地址）    §1.2 原先只登记了反向的读出值
flush_model → csr_control   cause、is_interrupt   §1.4 同样只登记了返回值
commit_unit → csr_control   csr_clear            §1.3 未登记；该 event 是模块侧改设计时
                                                 新增的，本层当时没跟上
```

> 对账时曾补过第六条 `commit_unit → PCFile : head0_tag、head1_tag`，
> **后又随 `inst_pc` 一并删除**——见 D 项。

第三、四、五条**同源**：**一个带外部参数（或地址）的组合读口是两条边**——参数进去、值出来。
本层只登记了"值出来"。

**这一类已全库扫过一遍**（第 24 轮，Codex 执行）：`Buffer` 的 head 与恢复读口、
`INT/FP_ARF`、`INT/FP_DST_REG`、`PCFile` 的恢复读口、`csr_control` 的两个读口，
**两半均齐全**；上表第五条是这次扫出来的唯一漏网。库外的 CSR FU 无 ⑥ 可核，豁免。

**B. 本层的命名错（1 处，责任在本层）**

`commit_unit → §2.1 装配` 原写作 `Commit_CDB[k].data`，已改为 `commit_data[k]`——
总线名只用于叙述整组线，公式与接口一律用扁平信号名。
本层原先对两条 CDB 处理不一致：bypass 那条写的是 `bypass_data[b]`（对的）。

> **一处曾被误报、现已撤销**：本层的 `INT_DST_REG → p1_check_resolve : tag、busy` 用本名，
> 而消费方写 `INT_DST_REG[rsX_idx[s]].tag`——**这不是不一致**。
> 冻结的是**本名** `tag`；前缀是**消费方补的路径**（它的接口没有"源模块"列）。
> 本层有源模块列，用本名与拥有方一致，**是对的**。

**C. 模块文档的真缺陷（1 处，责任在模块）**

`flush_model` 在 in-event 声明了"我收 `trap_vector(...)` 的返回值"，
却**没在 out-event 声明"我驱动 `cause` / `is_interrupt` 出去"**——
而同一份文档对 `flush_tag` 是声明了的（`组合读(out)；flush_tag —— 作两个恢复读口的地址`）。

这不是偶然，是**一类盲区**：带参数的读口，写文档时感觉是"我读了一下"，
实际是两条边；消费那一半记得写，驱动那一半容易漏。
已在 `flush_model` ④ 把两个参数显式命名（沿用 `trap_vector` 读口签名里的形参名，
不另起名——名字属于读口的拥有方）并补进 ⑥ out-event。
**全库其他带参数的读口须按同一形状复查。**

**D. 删掉的死接口：`commit_unit` 的 `inst_pc`（1 处）**

`commit_unit` ⑥ in-event 原有 `inst_pc`(64)，注着"**2 读口，仅 trace 用**"，
为此占用 `PCFile` 三个读口里的两个。但它的 ④、⑤、out-event **都没有它**——
值读进来就没了。查过 `v1_1`，那边同样只写"仅 trace 用"、**同样没说 trace 到哪儿去**，
所以这不是本轮重写弄丢的，是一直悬着的死接口。

**已删。** `PCFile` 读口 **3 → 1**（只剩 `flush_tag` 那个功能性的），
本层随之撤掉 `PCFile → commit_unit : inst_pc` 与 `commit_unit → PCFile : head0/1_tag` 两条边。

> **顺带否掉了一个规范提案**：曾考虑给规范加一档「可观测性端口」、对闭合规则豁免，
> 用来安放这类调试信号。否掉的理由——**一开口子，以后任何说不清去向的字段
> 都能塞进这一档，闭合规则就废了**。调试数据也必须是正常的 out-event，
> 并在本层有真实消费者。将来若要做 retire trace，按 `commit` event 的
> sideband 字段补（`trace_pc[k]`，采样时机由 `commit_valid[k]` 定），不另开档。
>
> **另纠正一处误判**：曾以为"顶层拿 `commit_tag` 自己查 PCFile"能把读口从 3 降到 1。
> **不能**——那只是把两条退休读口从 `commit_unit` 名下挪到顶层名下，物理上仍是三口。
> 省读口的唯一办法就是**真的不做 retire trace**，也就是现在这个选择。

**E. 模块侧已在前几轮改掉的两处**（列此以免与上面混淆）

`commit_unit` ④ 的 `Commit CDB` 公式块曾用结构体形式，且前两行同义反复，已压成一行。
`csr_control` 的 tracker 清除原先在两处各算一遍 `is_serial`，已改为
`commit_unit` 发 `csr_clear`、`csr_control` 只做 `commit_tag == csr_inflight_tag` 的身份比对。

## 2. 胶水逻辑

**胶水逻辑 = 没有主人的组合逻辑**：它把若干子模块的输出组合起来再喂给另一些子模块，
而它的输出**不是任何子模块的 out-event**。

**判定**：先看有没有哪个子模块在其 out-event 里认领了这个信号——
**有主人就归那个模块，无主才进本层**。附加必要条件：本层的胶水逻辑**不持有状态**
（持有状态的东西应当独立成一个子模块）。

> 「引用了两个及以上子模块的输出」**不是判据**——任何模块的输入都来自多个模块，
> `p1_dsp` 的 `accept[s]` 就引用了 Buffer、ISQ、csr_control、p1_check_resolve、
> p1_isq_group_select 五家，但它是 p1_dsp 的职责，不是胶水。
> 同理 `isq_wr_en[g]` 由 `p1_dsp` 在其 out-event 里认领，归 `p1_dsp`，不在本层。

### 2.1 `ISQ_Payload` 装配

两个候选 slot 各装配一份完整 payload，供 4 个 `p1_ISQ_input_mux` 实例二选一。
**本节是 `ISQ_Payload` 的唯一 schema 定义处**——四个 `ISQ_Group` 各自只捕获其中一个子集。

**源数据选择**：对每个 `(slot s, source x)`，按 `p1_check_resolve` 给的 7 bit onehot0
`rs_data_sel_t[s][x] = {sel_arf, sel_commit[2], sel_bypass[4]}` 取值：

```text
sel_arf       → rsX_is_fp[s] ? FP_ARF[fp_read_idx[x]] : INT_ARF[rsX_idx[s]]
sel_commit[c] → commit_data[c]
sel_bypass[b] → bypass_data[b]
全零          → rsX_data[s][x] = 0
```

- 全零合法，表示本拍不采样该源；对应 `p1_check_resolve` 解析出 `WAIT_OVERLAY` /
  `WAIT_PRODUCER` / `!use_rsX`。此时 `rsX_ready` 由 `p1_check_resolve` 另行给出
- **`x = 3` 时三元式必走 FP 侧**，两步：
  `!use_rsX[s]` 时 `p1_check_resolve` 给出的选择码全零 ⇒ `sel_arf = 0`，三元式根本不被求值；
  故 `sel_arf = 1` 蕴含 `use_rs3[s] = 1`，再由上游契约 `use_rs3[s] ⇒ rs3_is_fp[s]`
  得该分支必取 `FP_ARF`。
  ∴ `rs3` 永不选 `INT_ARF`，§1 里 `INT_ARF` 只登记 `rs1/2_idx` 的 4 个读口
- 本层**不做任何 busy / tag 比较**——选择码已由 `p1_check_resolve` 唯一生成，
  `sel_commit` 与 `sel_bypass` 的固定优先级也在那里实现
- **`fp_read_idx[x]` 没有 slot 维度**，而选择是按 `(s,x)` 做的。两者靠下面这条论证对上。

  先统一名字：`FP_read_address_mux` 的选择位是 **IB 直送的 `is_fp_instruction[0]`**；
  `p1_dsp` 的双FP指令阻塞用的是 **`p1_check_resolve` 转发的 `fp0` / `fp1`**，
  而 `fp0 = is_fp_instruction[0]`、`fp1 = is_fp_instruction[1]`——同一个值走两条边。

  设本拍被接受的 slot `s` 有 `rsX_is_fp[s] = 1`。
  由上游契约「触碰 FP RF ⇒ `is_fp_instruction` 为真」得 `fp_s = 1`：

  ```text
  s = 0 ⇒ fp0 = 1                          ⇒ mux 选中 slot0 ✓
  s = 1 ⇒ fp1 = 1，而 accept[1] 的 guard 含
          双FP指令阻塞 !(fp0 ∧ fp1) ⇒ fp0 = 0 ⇒ mux 选中 slot1 ✓
  ```

  ∴ **被接受的那个 FP slot 必然就是 mux 选中的那个**。
  两个 slot 同为 FP 时双FP指令阻塞使 `accept[1] = 0`，slot1 不被接受，
  其 `sel_arf ∧ rsX_is_fp` 分支没有有效消费者。
  **双FP指令阻塞单独推不出这个结论**——必须配上"被接受"这个前提与 `accept[1]` 的 guard

**`ISQ_Payload` schema**：

```text
rs1_data / rs2_data / rs3_data        64 各     本节选出
rs1_ready / rs2_ready / rs3_ready      1 各     p1_check_resolve
rs1_wait_tag / rs2_wait_tag / rs3_wait_tag  4 各  p1_check_resolve
self_tag                               4        p1_check_resolve
FU_Group                               2        IB
imm_valid / imm_data                   1 / 64   IB
pc / pred_taken / pred_target_pc      64 / 1 / 64  IB
is_store / store_size                  1 / 2    IB
子码 / Full Decode 控制信号             待定     IB
```

`slot_ISQGroup[s]` **不进 payload**——它已被 `p1_isq_group_select` 译码成
`select_payload[g][0/1]`，而 mux 实例本身就代表目标 group。

**`rd_idx` / `rd_is_fp` / `use_rd` / `rd_write_enable` 也不进 payload**——
回写按 `tag_out` 寻址，目的寄存器信息在 alloc 拍就已存进 `Buffer` 表项
（**写入即定**，回写不覆盖），提交拍的 ARF 写与 DST_REG 清除都从 `Buffer` 取。
FU 算 result 不需要目的寄存器号，故这四个字段不必绕经 ISQ 与 FU 再回来。
`use_rd` 更是连 `Buffer` 都不存——它只是 `p1_check_resolve` 算 `rd_write_enable` 的中间输入。

**本层只有这一处胶水逻辑。** `isq_wr_en[g]` 虽然也是组合、也跨模块，但已由 `p1_dsp`
在其 out-event 里认领，按 §2 的判定归 `p1_dsp`。它与本节共用同一组
`select_payload[g][s]`，两处必须接同一根线。

## 3. 协议编排

一个 event fire 时多个子模块须按约定次序或优先级同时响应，而该次序不属于任何单个子模块。

### 3.1 `global_flush_late` 的同拍抑制

最高优先级全局门控，各模块同拍响应：

```text
IB                     禁 enqueue 与 dequeue，复位 rptr / wptr，valid_count ← 0
p1_dsp                 accept[0] = accept[1] = 0
ISQ_Group0..3          禁 dispatch / issue / bypass_capture，isq_valid ← 0
Buffer                 禁新的 writeback；按 §3.2 的次序落位指针，occupancy 清零
CompletionScoreboard   清未退休 tag 的 valid、exec_done、store_drain_requested、store_drain_done
INT_DST_REG / FP_DST_REG   所有投机 busy 清 0
csr_control            只清 csr_inflight_valid；架构 CSR 与 current_priv 不受影响
p3_arbiter_G0/G1       无状态，不接收也不转发；各 FU 以直达的该信号门控本地 winner_ack
各 FU / g3_lsu_iface   清投机执行态、completion hold/skid、未 drain 的投机 store buffer 项；
                       已完成 drain 的 store 不回滚
FE                     丢弃旧 fetch 队列，从 redirect_pc 重新取指
```

**不为任何模块生成第二份 valid/ready，也不延迟 flush。**

### 3.2 commit 与 flush 同拍

```text
Buffer 的指针落位，严格按此次序：
    head_new    = head + commit_count
    tail_new    = head_new
    occupancy_q ← 0
```

- **`commit_count` 是回滚边界，`flush_tag` 是读地址**，两者通路不同：
  `commit_count` 随 commit 事件直达 `Buffer`，**不经 `flush_model`**；
  `flush_tag` 与 `flush_valid` / `flush_kind` 一同送 `flush_model`，只用来读恢复上下文
- **commit 拍与 flush 拍用的是同一根 `commit_count`、同一个值**
- `Buffer` 的 `tail` 回滚**只看 `commit_count`，绝不看 `flush_tag`**——
  MISPREDICT / MRET 下 `flush_tag` 指向的是本拍**已退休**的条目
- `CompletionScoreboard` **不接收 `flush_tag`**：同一时钟边界先应用 commit tag 清除，
  再清其余仍活跃的投机 tag，故"flush 清除"不会取消同拍已完成的提交

### 3.3 采样约定对照

跨模块**相反**，三处必须逐个查，不可类推：

```text
Buffer.can_alloc_1 / can_alloc_2 / rob_empty     拍初值
IB.room_q                                        拍初值
ISQ_Group_g.isq_free_for_dispatch                含同拍 issue
```

含同拍 `issue` 的代价：把 `FU_ready` 拉进了 P1 准入判定的同拍组合路径，
`accept[s]` 要等 `FU_ready` 稳定后才成立。

### 3.4 同格写口次序

`INT_DST_REG` / `FP_DST_REG` 的同一格在一拍内可能被多方写：

```text
commit-clear 先 → 同格上更年轻的 alloc 覆盖它 → global_flush_late 压掉 alloc，全表回 FREE
```

结果：同拍里更年轻的 alloc 赢过 tag 命中的 commit-clear，而那条提交在架构上仍然生效。
`INT_DST_REG` 的 2 个 alloc 写口之间，同拍 WAW 留更年轻那个（slot1）的 tag。

### 3.5 组合环与打破点

分两类。

**一类是 §1 里真实存在的双向边对**，靠**字段级不相关**打破：

```text
p1_dsp              → p1_isq_group_select   slot0_fire_candidate
p1_isq_group_select → p1_dsp                slot_ISQGroup[0/1]、groups_distinct、select_payload

    这一对若字段级相关就成环。打破点：slot0_fire_candidate 只用 slot0-only guard，
    不得读 slot_ISQGroup[1]、groups_distinct 或最终 accept[1]；
    也不得把最终 accept[0] 接回 slot0 group 的选择

    打破点在【字段级不相关】，不在物理放置。slot0_fire_candidate 由 p1_dsp 认领，
    按 §2 的判定归 p1_dsp，本层不接管它；模块图上的表面双向连接不构成实际反馈
```

**另一类是潜在环，靠【不建那条边】打破**——所以它们在 §1 中根本不出现：

```text
若 p1_check_resolve 的同拍 RAW 命中改用 accept[0]（而非 slot0_present），
    将新增 p1_dsp → p1_check_resolve 一条边，与已有的
    p1_check_resolve → p1_dsp（slot_missed_wakeup 等）成环

若 FP_read_address_mux 的选择位改用 accept[0/1]（而非 is_fp_instruction[0]），
    将新增 p1_dsp → FP_read_address_mux 一条边，与已有的
    FP_read_address_mux → FP_DST_REG → p1_check_resolve → p1_dsp 成环
```

**非环，但决定组合深度**：

```text
组内各 FU → ISQ_Group_g（FU_ready）→ isq_free_for_dispatch → p1_dsp / p1_isq_group_select
    accept[s] 要等 FU_ready 稳定后才成立，见 §3.3
```

## 4. 全局核对

只有本层看得见全库的边集合，以下核对归本层：

- **每条 out-event 字段、每条 Static Info 是否真有消费者**——模块文档不写消费者
- **每条 in-event 是否有对应的 out-event 或 Static Info 供给**，字段名与位宽一致
- **同一根线在两端的名字**：总线名只用于描述整组线，公式与接口一律用信号名
  （`bypass_valid[b] = p3_bypass_CDB[b].valid`；`commit_valid[k] = Commit_CDB[k].valid`）
- **字段名全库冻结**：同一字段跨文档必须同名
- 库外边的传输语义是否已在 §1.5 补齐
