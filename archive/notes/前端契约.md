# 前端契约 · FE 与 decode 欠后端什么

**本文档只回答一件事：`IB_Payload` 的每个字段由前端如何产生，以及后端已经据以设计的上游不变式。**

FE 怎么取指、decode 怎么译——**一律不在这里**。两者都是**库外**单元，按既定范围划定
不写微架构文档；本文档写的是**契约**，即前端不满足就会让后端出错的那些约定。

**为什么需要这份文档**：`IB_Payload` 的字段语义散在 `IB微架构文档.md` ⑤，
分组与准入语义散在 `dispatch_logic微架构文档.md` ④，而三条上游不变式
**一份文档都没有拥有过**（`walkthrough.md` §2.4 一直挂着这个缺口）。
IMAFDC 补全后 decode 的义务又翻了一倍——22 条原子子码的属性、52 条压缩子码、
`ENABLE_*` 关闭时的 `illegal`、`SYS` 分类——再不给它一个宿主就散得收不回来了。

---

## 1. 三条上游不变式

**后端把它们当前提用，不做检查，不做兜底。** 前端违反即是错，而且是那种下游看不出来的错。

```text
① use_rs3[s] ⇒ rs3_is_fp[s]
   第三源只可能是 FP。据此 INT_ARF 只开 4 个读口（rs1/rs2 × 2 slot），
   §2.1 装配里 rs3 永不选 INT_ARF

② 触碰 FP 寄存器堆 ⇒ is_fp_instruction 为真
   包括 FP load / store（它们落 G3，但仍是 FP 指令）。
   据此 dispatch 的「双 FP 阻塞」!(fp0 ∧ fp1) 才成立，
   而那一条又是 FP_ARF 单写口 / FP_tag_mapping 单清除口的依据

③ fe_valid 是两位有序前缀
   fe_valid = 00 / 10 / 11，不存在 01。slot0 无效时 slot1 必须也无效。
   据此 IB 的 enqueue 才能按前缀入队、不跳洞
```

未被接受的候选，FE **须保持有序后缀、下拍重发**（`accepted_slot` 是回压指示，不是握手）。

## 2. `IB_Payload` 字段的产生义务

总逻辑宽度 **302 bit**；**packed 字段顺序刻意不冻结**，属实现。

```text
字段                        decode 的义务
──────────────────────────────────────────────────────────────────────
pc                          本条指令的地址
inst_bits(32)               本条指令的**原始编码**。压缩指令只用低 16 位、高位置零
is_compressed               本条是不是 16 位指令。可由 inst_bits[1:0] != 2'b11 判，
                            但仍单列——它是所有指令都有的通用属性
is_serial                   见 §3。覆盖四类：CSR 指令、MRET、FENCE/FENCE.I、22 条原子指令
is_fp_instruction           见 §1 ②
rs1/2/3_idx、use_rs1/2/3    源寄存器号与使用位
rs1/2/3_is_fp               该源取自哪个寄存器堆；rs3 恒为 1（见 §1 ①）
rd_idx、use_rd、rd_is_fp    目的寄存器。x0 的抑制由后端的 rd_write_enable 承担，
                            decode 照实填 use_rd 即可
is_store                    **专指"走 SCB drain 子流程的普通缓冲 store"**。
                            原子指令会写内存但 is_store = 0
mem_funct3(3)               访存类型：同时承载宽度、符号扩展与 FP 三件事。
                            load 侧七种取值装不进 2 bit，故为 3 bit
imm_valid、imm_data         **已译码的立即数**，不是原始编码。原子指令 imm 恒 0
pred_taken、pred_target_pc  分支预测结果，只有 BRU 用
exe_subop(24)               = {format[1:0], opcode_or_op[6:0], funct3[2:0], high_fixed[11:0]}
                            format = 01 普通 32 位；10 = RVC
                            FP 的 .S/.D 精度由高位固定段区分，不另设 fmt 字段
                            子码全集见 module_spec_v2/subop/exe_subop_pkg.sv
full_decode(17)             = {csr_write_intent, illegal, rm[2:0], csr_addr[11:0]}
                            rm 编码 000..100 = RNE/RTZ/RDN/RUP/RMM，111 = DYN，101/110 保留
                            不适用时置零忽略
```

**`csr_write_intent` 是后端唯一推导不出来的一位,必须由 decode 给。**
register-form 的 `CSRRS` / `CSRRC` 是否真写 CSR，取决于 **`rs1_idx == x0` 这个寄存器号**，
**不是 `rs1_data == 0` 这个值**——而 `rs1_idx` 不进 ISQ payload（只带 `rs1_data`）。

```text
csr_write_intent = 1   CSRRW / CSRRWI                     恒写
                       CSRRS / CSRRC   且 rs1_idx != x0
                       CSRRSI / CSRRCI 且 uimm != 0
                 = 0   其余（含全部非 CSR 指令）
```

少了它有两处会错：① `csrrs t0, fcsr, x0` 是**纯读**，被当成写会让 apply 路径置
`FS ← Dirty`，而"CSR 读不置脏"是既定口径；② 只读 CSR 的**读合法、写非法**，
分不开就只能一刀切。v1 RTL 的 `csr_unit.sv` 用的正是
`csr_write_en && csr_write_intent && legal_csr_addr` 三项相与。

**`FU_Group` 不进 payload**——它是 `exe_subop` 的纯函数，由 dispatch 导出。

**`inst_bits` 与 `imm_data` 不可互相替代**：前者是原始编码，`tval` 只能从它取；
后者是已译码的立即数，压缩指令的 16 位编码更与立即数无对应关系。

## 3. 各指令类的译码属性

```text
类               组        is_serial  is_store  use_rd   备注
─────────────────────────────────────────────────────────────────────────────
ALU 可分流        G0/G1 动态    0         0        1      两集合都在
ALU G0-only       G0            0         0        1      AUIPC：要算 pc + imm，G1 不存 pc
BRU               G0            0         0        看指令   JAL/JALR 写 rd，条件分支不写
MRET              G0            1         0        0      串行是因为要读架构 mepc
ILLEGAL           G0            0         0        0      无源操作数
SYS               G0            0         0        0      ECALL / EBREAK / WFI，无源操作数
CSR               G0            1         0        1      uimm 占 imm 通道，csr_addr 走 full_decode
DIV               G0            0         0        1
MUL               G1            0         0        1
FPU               G2            0         0        1
LSU load          G3            0         0        1      含 FP load：is_fp_instruction = 1
LSU store         G3            0         1        0      含 FP store：rs2_is_fp = 1
ATOMIC            G3            1         0        1      22 条；rs1 = 地址、rs2 = 操作数、imm 恒 0
FENCE / FENCE.I   G3            1         0        0      无源操作数
```

**`is_serial` 的两类理由**：CSR 与 MRET 是因为要读写架构状态；
`FENCE`/`FENCE.I` 与原子指令是因为要在访存序上取得"更早的访存已全部退休"这个**结构性前提**——
后者是 A 扩展正确性的落点，不是性能取舍（理由链见 `walkthrough.md` §1.19）。

**`ECALL` / `EBREAK` / `WFI` 不串行**：它们不读写架构状态，效应全在退休侧，
顺序由按序退休保证。

## 4. `illegal` 的产生义务

```text
illegal = 1 的三类来路
──────────────────────────────────────────────────────────
① 编码本身非法（未定义 opcode、保留字段取了保留值等）
② ENABLE_A = 0 时的全部 is_g3_atomic_subop
③ ENABLE_C = 0 时的全部 SUBOP_C_*
```

**FP 指令的合法性检查不在 decode，一条也不在。** `mstatus.FS == Off`、`rm` 保留值、
`rm = DYN` 而 `frm` 保留——三种情形**全部由派遣侧统一判**，decode 只管照实填
`is_fp_instruction` 与 `full_decode.rm`。

**为什么不让 decode 分担静态那一半**：`rm ∈ {101,110}` 确实是静态可判的，
但 `FS == Off` 与 DYN 两种情形只有读得到架构状态的派遣侧能判。
**判据分两处写就会漂移**，而这是一条会让机器"静默算错而不是陷入"的判据——
宁可只有一个主人。见 `FU契约.md` §7。

**取指故障不走 `illegal`，走 `FETCH_FAULT` 子码。** FE 检出取指故障后告知 decode，
decode **直接产出 `FETCH_FAULT` 子码**，`IB_Payload` 一位都不加：

```text
FETCH_FAULT   与 ILLEGAL 同形：G0 · requester 0、use_rs/rd = 0、is_serial = 0
              唯二不同：cause = 1（指令访问故障）、tval = pc（不是 inst_bits）
```

**为什么不能塞成 `illegal = 1`**：cause 必须是 1 不是 2，而本库的口径是"cause 由子码硬编码"。
**也不能在 payload 里加一位异常标志让 FU 去选**——那等于把 cause 搬进 payload。

**为什么这条通路必须存在,即使当前检不出**：一条取指失败的指令仍然要占一个 tag，
而 `exec_done` 只能由完成 lane 置位；没有 FU 为它发 `Result_valid`，队头就永远卡死。
**检出**要等内存映射，**通路**与检出无关、现在就得定。
（这条是对照真实环境的 FE 接口发现的——那边 `fe_be_info_t` 有 `excp_vld` 字段，
而我们全库没有任何取指异常通路。）

**②③ 必须走 `illegal`，不能靠 `subop_supported_now = 0`。** 后者的后果是该 slot
**永不 `accept`、永远停在队头**——是挂死不是陷入。RISC-V 要求未实现的指令报非法指令异常，
只有 `illegal = 1` 的 ILLEGAL 完成路径做得到。
`subop_supported_now = 0` 只保留给 `SUBOP_INVALID` 与真正未被任何集合覆盖的编码，
是"decode 出错"的兜底，正常运行中不该命中。

**`illegal = 1` 时 `exe_subop` 取兜底值**（`SUBOP_INVALID`），
由 dispatch 固定送 G0 的 ILLEGAL 完成路径；`cause` 由子码硬编码、不进 payload；
`tval` 取 `inst_bits`（压缩指令取 `{48'b0, inst_bits[15:0]}`）。

**④ 只覆盖静态保留值。** `rm = DYN` 而 `frm` 取到保留值、以及 `mstatus.FS == Off`
这两种情形是**动态**的，decode 看不到，由派遣侧读架构状态合成——
见 `module_spec_v2/checked_file/dispatch_logic微架构文档.md` ④ 与 `FU契约.md` §7。

**`ENABLE_*` 必须与 `misa` 同源。** 同一组静态参数驱动 decode、FE、LSU、FPU 与 `misa`；
三处各自为政就会出现"`misa` 说有、硬件没有"或反之，而 lockstep 的 ISS `--isa` 又是照
`misa` 配的——发散会出现在离病灶很远的地方。前置条件见 `异常与trap语义.md` §6。

## 5. FE 侧

### 5.1 取指

```text
ENABLE_C = 0   取指粒度 4 字节，指令恒 32 位
ENABLE_C = 1   取指粒度 2 字节；且必须支持 pc[1] = 1 时
               跨两个 32 位 fetch word 拼出一条 32 位指令
```

指令长度自描述：`inst[1:0] != 2'b11` 即为 16 位。

### 5.2 重定向

FE **不收 `global_flush_late`**，只收 `redirect_*`——它不是投机状态的持有者，
要的是"从哪重新取指"，不是"清掉什么"。这一条接线时最容易搞错
（理由见 `walkthrough.md` §1.10）。

```text
redirect_valid / redirect_pc / redirect_kind(3) / frontend_icache_invalidate

redirect_kind：0 MISPREDICT  1 EXCEPTION  2 MRET  3 INTERRUPT  4 FENCE_I
```

**`frontend_icache_invalidate` 由 `flush_model` 产生，FE 不自己译 `redirect_kind`。**
它为 1 时，FE 须清 fetch queue、预取，以及 I-cache 中需要失效的状态。
重定向的性质归 `flush_model` 解释，FE 只按线动作。

### 5.3 回压

```text
accepted_slot[1:0]   触发。未接受的候选须保持有序后缀、下拍重发
```

**后端不导出剩余容量**，FE 也不需要它。协议是**盲发 → 读回实收 → 滑窗**：
FE 有几条摆几条，后端同拍回 `accepted_slot`，FE 下拍按它推进发送指针。

**为什么不给容量提示**：后端的接受判据**含本拍出队**——上一拍缓冲满、本拍出队 2 条时，
同一拍就能收 2 条。任何容量值送到 FE 手里都已经滞后一拍，照它限流是净亏。
理由链见 `walkthrough.md` §1.29。
