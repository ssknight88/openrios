# 缺口清单（方案.md:13 §0 交付物之一）

> 记法：按 Mnemonic 记「这条指令有哪部分内容填不进 A 卡、归三模块的哪一项、为什么现在填不进」。
> 本轮范围 = `RVA23_IMAFDC_Classification.xlsx` 208 条；**208 条全部已铺**（RV64I 56 · M 13 · A 22 · Zicsr 6 · Zifencei 1 · F 30 · D 32 · C 36 · Zcb 12）。
> A 卡是实验（方案.md:3）：本文件不提模板改法，只记事实。改不改由 review 定（方案.md:157 §3.4）。

## 一句话

**208 条全部铺完，80 条内容完全填进 A 卡，128 条至少有一项填不进。** 128 这个数看着大，拆开看：48 条压缩指令全部因 ⑭⑯（指向本体 · 16 位记法，两条是同一件事的两面）计入；62 条浮点全部因 ⑤（fflags/frm/FS 是 C 项）和 ⑱（元组 let）计入。去掉这两类**格式记法**问题，真正「语义放不下」的是 ②③⑥⑧⑩⑪⑫ 共 17 条。

| 桶 | 张数 | 完全填进 | 有填不进 | 主要原因 |
|---|---|---|---|---|
| RV64I | 56 | 46 | 10 | ②③④⑤⑥⑦⑧⑨ |
| M | 13 | 9 | 4 | ⑬ div/divu/divw/divuw 的 let 同名重绑定 |
| A | 22 | 18 | 4 | ⑩⑪ lr/sc |
| Zicsr | 6 | 0 | 6 | ④⑤⑨⑫ |
| Zifencei | 1 | 0 | 1 | ② |
| F | 30 | 0 | 30 | ④⑤⑱（fflags · FS · 元组）|
| D | 32 | 0 | 32 | 同 F |
| C | 36 | 0 | 36 | ⑭⑯（+⑮⑦⑧⑨ 部分）|
| Zcb | 12 | 0 | 12 | ⑭⑯（+⑰ 5 条）|

缺口编号 ①–⑱：①⑦⑧⑨⑪⑫⑬⑭⑮⑯⑰⑱ 归 A 自身（① 已关），②⑥ 归「序」，③④⑤ 归 C，⑩ 归 C 或「序」未定。卡内用同一套编号标注，`grep -rn "填不进" cards/` 捞全。

## 归 B / 序 —— B 模板未定，A 卡装不下（3 条）

方案.md:33 §1.2 原话：「状态机视角：C 状态 · A 转移 · B 约束 · **序第四项**。本方案只做 A」。
A 卡七步问的全是「这条指令自己读了什么 · 算了什么 · 写了什么」，下面这 3 条的核心语义不是「自己干了什么」。

| Mnemonic | 填不进的是什么 | 归哪项 | 为什么 |
|---|---|---|---|
| `fence` | `pred` / `succ` 指定的读写次序约束 | 序 | 它约束的是**别的指令**的先后，不是自己的状态转移。七步没有描述跨指令关系的槽位。卡上七格全填合法的 `null` / `[]`，语义为零 |
| `sfence.vma` | `flush_TLB(asid, vmid, addr, S_Stage \| VS_Stage)` | 序 | 同上。方案.md:106 §2.6 已登记，样例卡 `cards/I/sfence.vma.yaml` 自己已在 `memory:` 段注明 |
| `fence.i` | `sail_barrier(Barrier_RISCV_i)`——此前的存储对此后的取指可见 | 序 | 同 fence。Sail 文件内注释「fence.i is a nop for the memory model」，子句只有这一句 |
| `wfi` | 「停住直到有中断待处理」的等待态 | 序（时间） | `outcome.retire` 取值只有 `normal \| never`，装不下第三态「既没完成也没陷入」。七步描述一次瞬时转移，转移之间的时间不属于任何一步 |

三条共同点：**卡填得满、lint 会过、覆盖矩阵会记「显式 N/A ✓」，而指令语义一个字没上卡。** 这是方案要消灭的隐式空格换了个位置出现，必须在本清单里显式记着，不能只靠卡上的 `null`。

## 归 C —— C 模板未定，A 卡不知道该登记什么（2 条）

方案.md:33 §1.2：「卡里碰到 CSR 写只登记 `CSR.field` 名，不展开」。问题不在「不展开」，在**登记什么名字**没有规矩。

| Mnemonic | 填不进的是什么 | 归哪项 | 为什么 |
|---|---|---|---|
| `mret` | `cur_privilege ← privLevel_of_bits(mstatus[MPP])` | C（状态） | `cur_privilege` 是架构状态，但既不是通用寄存器、又没有 CSR 地址、也不是 PC。`update` 的三个槽（regs / csr / next_pc）是按状态的**载体**分的，它是第四种载体。它算不算 C 项、该怎么登记，要 C 模板定 |
| `mret` | `mstatus.MPRV` 的**条件**写（返回目标非 M 才置 0） | C（状态的写入规则） | `update.csr[]` 的元素是 `{csr, field, value}` 无条件赋值，没有 `when`。卡上现在写成无条件，是错的，已在卡内标 `⟨待核⟩` |
| `sret` | 同上两条 | C | 同上 |
| `sret` | 写的到底是 `mstatus` 还是 `sstatus` / `vsstatus` | C（视图） | 同一块硬件三个名字、三个可见子集。卡上「写哪个寄存器」只能填一个名字，填 `mstatus` 对但操作系统眼里叫 `sstatus`，填 `sstatus` 对但漏了状态更大。**本卡一律写 `mstatus` 名，是我挑的，无依据**，等 C 模板定 |

| `csrrw` `csrrs` `csrrc` `csrrwi` `csrrsi` `csrrci` | CSR 写只在 `access_type != CSRRead` 时发生（csrrs/csrrc 的 rs1=x0、csrrsi/csrrci 的 uimm=0 只读不写） | C（④ 条件写） | `update.regs[]` 无 `when`。6 张全撞 |
| 同上 6 张 | 落进 CSR 的是 `write_CSR` 返回的 `final_val`（WARL 合法化后），不是卡上的 `write_val`；写哪个物理寄存器、哪个视图由运行时的 `csr` 字段定 | C（⑤ 视图 / 落值） | 卡上只能写 `{type: csr, id: csr, value: write_val}` |
| 同上 6 张 | `check_CSR_result(csr, cur_privilege, access_type)`：按地址位判特权级 / 只读 / 存在性 | C（access 行） | 卡上写成两条 `conditions`，但判定表在 C 卡 |

| 62 条 F / D | `accrue_fflags`：`fcsr[FFLAGS] = fcsr[FFLAGS] \| flags`，然后 **按 `fflags_dirty_policy` 条件地** `dirty_fd_context_if_present()`（Precise：fflags 变了才置 · Flag：flags ≠ 0 才置 · Instruction：恒置） | C（④ 条件写） | 卡上写成无条件。对同时写 F 寄存器的指令等价（`wF` 无条件调 `dirty_fd_context()`）；对只写 X 的 fcvt.w.s · feq/flt/fle 等 **不等价**，已在卡内标明 |
| 62 条 F / D | `fflags` 是 `fcsr[4:0]` 的视图（`read_CSR(0x001) = zero_extend(fcsr[FFLAGS])`）；`dirty_fd_context` 在 `inVirtualPrivilege()` 时还写 `vsstatus[FS]` / `[SD]` | C（⑤ 视图） | 登记 `fcsr.FFLAGS` 还是 `fflags`，登记 `mstatus.FS` 还是同时 `vsstatus.FS`，无规矩 |
| 62 条 F / D | `select_instr_or_fcsr_rm(rm)` 读 `fcsr[FRM]`，非法值按 `fcsr_rm_reserved_behavior` 选 Fatal / Illegal | C（`fcsr.FRM` 的合法值域）+ B（param） | 已按 §2.4 第一条边界放进 `conditions[].params`，不进 `implicit_reads` |

副产物（记着，不单列）：`mret` / `sret` 的 `calculate` 算出 `prev_priv` 却没人消费——因为消费它的那个槽（写 `cur_privilege`）不存在。方案.md:172 §4.2 第 4 项「out 名闭合」只查「引用的 out 有定义」，查不出「定义的 out 没人引用」，所以这种悬空 out 现在是查不出来的。

## 归 A 自身 —— 实验结果（① 已关；⑦⑧⑨⑪⑫⑬⑭⑮⑯⑰⑱ 开着；⑩ 归属未定）

这几条跟 B / C 无关，是 A 模板试出来的。①⑧⑨ 三条是 2026-09-10 取到 Sail `803f192b` 原文后重新定位的结果。

### ① 次序：嵌套压平 —— `jal` `jalr`（另波及 6 张分支卡）—— **已关（2026-09-10）**

关掉的依据是 方案.md §2.1 新增的三句和 §2.3 第 6 条，不改键：

- 七步之间没有执行顺序，只是分类格子 → 「卡面读起来先写 rd 后抛异常」不成立，没人从上往下读
- 唯一原子性规则「任一 exception 成立 ⇒ `memory.request.write` 与 Update 全部不发生」→ `X(rd) = link_address` 嵌在成功分支里这层关系，是全部 208 条共有的全局不变量，写在 schema 一处即可，卡上不表达不算丢（`lw` `amoadd.w` 样例卡本来就是这么处理的）
- §2.3 第 6 条「if → when，内层条件用 `&` 粘外层守卫」→ 分支卡上的 `taken &` 有了依据，不再是「发明的动作」

**暂定性质**：第 6 条写明「撞到 `when` 表达不了、或与语义冲突的，报出来」。已知三个槽没有 `when`（`update.regs` · `update.csr` · `memory.request`），`sc.w` / `sc.d` 的条件访存、`csrrs` / `csrrc` 的条件 CSR 写会撞上，届时按第 6 条上报。

以下是关掉前的原始记录，留作依据：

Sail 用**嵌套**表达次序：

```sail
function clause execute JAL(imm, rd) = {
  let link_address = get_next_pc();
  match jump_to(PC + sign_extend(imm)) {
    Retire_Success() => { X(rd) = link_address; Retire_Success() },
    failure => failure,
  }
}
```

`X(rd) = link_address` 写在 `match jump_to(...)` 的 `Retire_Success()` 分支**内部**，失败分支 `failure => failure` 根本不碰 rd。

A 卡只能写成两句平行的话——`update.regs` 一句、`outcome.exceptions` 一句——**「前者从属于后者的成功分支」这层关系没有任何键能表达**，而模板把 `update` 排在 `outcome` 前面，卡面读起来正好相反。

方案.md:63 §2.1 只画了一条时间线「Memory 在 Update 前，fault 时 arch state 未动」，它假设所有 fault 来自 Memory。`jal` 的 fault 来自 Calculate（step 4）算出的 `target`：检查点该在 step 4 之后、Update（step 6）之前，七步里没有这一步；`dynamic_check` 是 step 2 够不着 `target`，只剩 `outcome`（step 7），而 7 在 6 后面。

**同一个压平在 6 张分支卡上也留了痕迹**：Sail 的 `taken` 是 BTYPE 子句的外层 `if`，`jump_to` 只在 taken 时被调用；平铺后外层 `if` 没有落点，只能把 `taken &` 合取进 `outcome.exceptions[].when`。那个 `taken &` 不是 Sail 原话，卡内已注明。

### ⑦ XLEN 编码分歧 —— `slli` `srli` `srai`

RV32 下是 7 位固定 + `shamt` 5 位（20:5），RV64 下是 6 位固定 + `shamt` 6 位（20:6）。`decode.encoding` 只有一份；`decode.xlen: null` 回答的是「在哪些 XLEN 下**存在**这条指令」，不回答「编码是否随 XLEN 变」。本卡按 RV64 实例化填。方案.md:75 §2.3 第 3 条只规定了**语义**按 RV64 实例化，没规定编码。

### ⑧ 扩展钩子无槽，落槽率破 100% —— `jalr`

`jalr_seq.sail` 的 JALR 子句第一句是：

```sail
  update_elp_state(rs1);
```

这是 Zicfilp（landing pad）的状态更新。七步无槽：不是通用寄存器写、不是 CSR 写、不是访存。它也不属于 方案.md:77 §2.3 第 5 条允许剥掉的四类噪音——类型/断言、`Ok/Err` 包装、读序调整（issue #1761）、非本指令分支——**一类都不沾**。按该条「其它落不进的是缺口，不是噪音」，判定为缺口。

复杂之处：Zicfilp 本身**不在**本轮范围（指令清单.md:167 明确把 Zicfilp 列进「排除了什么」）。但这句话确实在子句里，而方案.md:166 §4.1 要求落槽率 100%。两种可能的处置——给 §2.3 第 5 条加第五类噪音「未启用扩展的钩子」，或者给七步开槽——都属格式变更，方案.md:157 §3.4 规定由 review 定。本清单只登记，不建议。

### ⑨ 扩展检查的 cause 写不出来 —— `jal` `jalr`（`beq` 等 6 张同源）

`jump_to` 的第一句是与对齐检查**并列的第二条异常路径**：

```sail
  match ext_control_check_pc(target) {
    Some(e) => return Ext_ControlAddr_Check_Failure(e),
    None()  => (),
  };
```

`outcome.exceptions[].cause` 要求写 Sail 的 `ExceptionType` 名（方案.md:30 A 卡模板「来源」段），而这条的 cause 由扩展（Zicfilp / CFI）在运行时给出，卡上写不出具体名字。8 张跳转/分支卡目前都只写了对齐那一条，**这条路径全部缺失**。

源到手后确认这是一整族：`sys/insts_begin.sail` L16 的 `ExecutionResult` 有四个 `Ext_*` 构造子——`Ext_CSR_Check_Failure`（Zicsr 6 张）· `Ext_ControlAddr_Check_Failure`（跳转分支 8 张 + 压缩 5 张）· `Ext_DataAddr_Check_Failure`（`sys/vmem_utils.sail` L326 / L341 的 `get_transformed_data_addr`，**所有访存指令**：I 的 11 张 + A 的 22 张 + F/D 的 4 张 + 压缩访存 16 张）· `Ext_XRET_Priv_Failure`（mret / sret）。合计 **70 余张**，全部是同一个形状：扩展钩子的失败路径既进不了 `dynamic_check`（raise 枚举只有两个）也进不了 `outcome`（cause 写不出）。

（`jump_to` 里的 `assert(target[0] == 0b0)` 属于 §2.3 第 5 条的「类型/断言」，已按规矩剥掉，不计缺口。）

⑨ 在 Zicsr 上再撞一次：`doCSR` 的 `if not(ext_check_CSR(csr, cur_privilege, access_type)) then Ext_CSR_Check_Failure()`。它在「拒绝执行」的位置，但 `raise` 枚举只有 Illegal / Virtual，进不了 `dynamic_check`；cause 由扩展给，也进不了 `outcome`。6 张 Zicsr 全撞。

### ⑩ 保留集无槽 —— `lr.w` `lr.d` `sc.w` `sc.d`（归 C 或「序」，未定）

```sail
// LOADRES
match vmem_read(rs1, zeros(), width, LoadReserved(aq, rl, Data), aq, aq & rl, true) { … }
// STORECON
match vmem_write(rs1, zeros(), width, data, StoreConditional(aq, rl, Data), aq & rl, rl, true) {
  Ok(b) => { X(rd) = zero_extend(bool_bit(~(b))); cancel_reservation(); RETIRE_SUCCESS },
```

LR 建立保留集（`LoadReserved` 访问类型 + 末参 `true`），SC 消费并取消它（`cancel_reservation()`）。保留集是架构状态，但既非通用寄存器、非 CSR、非 PC——**与 ③ 的 `cur_privilege` 同形，是第四种载体**。卡上只能靠 `memory.request.type: LR | SC` 暗示，没有槽写「建立 / 取消了对 vaddr 的保留」。`cancel_reservation()` 这一行落槽表落不进任何格。方案.md:135 §3.3 点名 lr.w · sc.w 要逼的「reservation」就是它。归哪一项要 review 定：它是状态（C）还是跨指令关系（序）？两说都成立。

### ⑪ SC 成功位无定义槽 —— `sc.w` `sc.d`

`update.regs` 写 `zero_extend(bool_bit(~(b)))`，`b` 是 `vmem_write` 的返回值 `Ok(b)`——既不是 Calculate 的产物、也不是 read 回来的数据。`memory.request` 只有 read / modify / write 三个出口，**没有「写操作返回一个值」的出口**。两张卡故意不定义 `b`，让 out 名闭合（方案.md:172 §4.2 第 4 项）在这两张卡上红掉，作为机器可见的缺口信号。最便宜的候选是挂到 `read: {out: b, width: 1}`，但那是把「读回值」当「写结果」用，语义不对。方案.md:135 §3.3 点名的「SC 成功位」就是它。

### ⑫ 依赖层冲突 —— 6 张 Zicsr

```sail
match write_CSR(csr, write_val) {
  Ok(final_val) => { … RETIRE_SUCCESS },
  Err(())       => Illegal_Instruction(),
}
```

`write_CSR` 失败抛 `Illegal_Instruction`。按 方案.md §2.1（2026-09-10）「raise 种类」分界，它该进 `dynamic_check`（step 2）；但它依赖 `write_val`，那是 Calculate（step 4）的 out——**与 §2.1 同日写下的「第 N 步只能引用前面步骤的 out」正面冲突**。这是 §2.3 第 6 条要求上报的情况。6 张卡两边都没写，等裁决。

可能的出路（只列不选）：(a) 放 `outcome.exceptions`，cause 写 `ExceptionType` 名 `E_Illegal_Instr`——那 §2.1 的分界要改成「按 Sail 的名字空间：`ExecutionResult` 名进 dynamic_check，`ExceptionType` 名进 outcome」；(b) 承认 dynamic_check 可以引用 Calculate 的 out——那「依赖层」的说法要改。

### ⑬ let 同名重绑定 —— `div` `divu` `divw` `divuw`

```sail
let quotient = if rs2_int == 0 then -1 else quot_round_zero(rs1_int, rs2_int);
let quotient = if not(is_unsigned) & quotient >= 2 ^ (xlen - 1) then negate(2 ^ (xlen - 1)) else quotient;
```

Sail 两个同名 `let`，后者遮蔽前者（处理有符号溢出 -2^63 / -1）。方案.md:74 §2.3 第 2 条「out 名 = let 名」在此产生两个同名 out。卡上照抄两条：第二条右侧的 `quotient` 指第一条，后续引用指第二条。out 名闭合（方案.md:172 §4.2 第 4 项）按「名字存在」查，**查不出这种歧义**。

### ⑭ 指向本体无槽 —— 48 条压缩指令（C 36 + Zcb 12）

Sail 里压缩指令的 execute 几乎全是一行 `ExecuteAs(本体(…))`：

```sail
function clause execute C_ADDI(imm, rsd) = {
  let imm : bits(12) = sign_extend(imm);
  ExecuteAs(ITYPE(imm, rsd, rsd, ADDI))
}
```

方案.md:64 §2.1 早写了「别名 / 压缩指令只有 Decode + 指向本体（待第一批实验）」。**实验结论：模板没有「指向本体」的键。** 本轮做法：Decode 全填（这是压缩指令真正不同的地方），其余六步按本体展开、操作数代换，本体的 `ExecuteAs(...)` 原话写在卡头注释。代价是 48 张与本体重复；好处是列查询（方案.md:20 §1.1）在压缩卡上仍能工作——rename 拉操作数个数、dispatch 拉 mnemonic，不用先跳到本体。要不要开 `decode.expands_to` 之类的键，review 定。例外：`c.zext.b` `c.not` 是直接写 `X(rsd) = …`，不经 ExecuteAs。

### ⑮ 固定寄存器无操作数槽 —— 16 条压缩指令

`c.lwsp` 的基址是 `sp`、`c.jalr` 写 `ra`、`c.li` / `c.mv` / `c.beqz` 的一个源是 `x0`——都不在编码里。`operand_fetch.operands[].id` 必须是 `encoding.fields` 的名。本卡做法：读侧放 `implicit_reads: [X(sp)]`，写侧 `update.regs[].id` 直接写 `sp` / `ra`，x0 在 `op` 里直接写 `X(zreg)`。三种写法都是权宜，卡内注明。

### ⑯ 16 位编码记法未定义 —— 48 条压缩指令

### ExecutionResult：②⑥⑨⑭ 的共同根

union ExecutionResult = {

  ExecuteAs      : instruction,      // 压缩指令委托本体            → ⑭
  Enter_Wait     : WaitReason,       // WFI / WRS 进入等待态         → ⑥
