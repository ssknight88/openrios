## B. system_instruction_handler（scoreboard 组第四子模块）

### 推荐案（贴参照：参照无 csr_file 条目，架构寄存器就住在 handler 里）

新文档 `system_instruction_handler微架构文档.md` = **csr_file 全文重组 + SCB 的 csr_stage 迁入 + 系统指令待补挂点**：

- **状态**：架构 CSR 三组（trap/特权组、最小合规组、计数器）+ `current_priv` + **csr_stage**
  （组内唯一投机寄存器；原 csr_file"flush 完全不动"改述为"架构寄存器 flush 不动，csr_stage 随 flush 作废"）
- **事件**：capture（监听 lane 0 的 is_csr/we/csr_addr/csr_wdata）；apply（commit lane tag 比对 → 内部落笔，`arch_csr_write` 从跨模块事件降级为模块内一行）；`trap_entry` / `mret_update`（收自 flush_model，判读与执行都在本模块）；计数器自增（收 commit_count）
- **待补挂点**：fence.i（mispredict 技巧注记迁入）、sfence.vma（S 态，远期）、ECALL/EBREAK cause 细则——IB ⑤ 的待补注记保留但改为指向本文档
- **读口不变**：软件读口（csr_fu）、current_priv、trap_vector/interrupt_pending/interrupt_cause/mepc，按消费者分侧组织照旧

连带改动：`csr_file微架构文档.md` 删除（内容并入）；CompletionScoreboard 删 ③ capture/apply、⑤ csr_stage、⑥ lane0 附加字段与 arch_csr_write 产物；flush_model 的 trap_state_write 对端改名；Module.md scoreboard 组下列四子模块。

**⚠ 需要你确认的冲突点**：你早前拍过"csr_stage 就放进 SCB"。按参照的新口径 **scoreboard 是组**（四个子模块的集合），csr_stage 从 CompletionSCB 迁到同组的 system_instruction_handler 仍在"scoreboard 里"——若你当时指的就是 CompletionSCB 本体，用备选案。

### 备选案（结构改动最小）

csr_stage 留在 CompletionSCB；system_instruction_handler = 原 csr_file 改名重挂 + trap 两路判读 + 待补挂点；`arch_csr_write` 仍由 SCB 发。代价："csrrw mstatus 的处理"被切成两半（stage 在 SCB、落笔在 handler），与参照把 csrrw 列在 handler 名下的口径稍逊。
