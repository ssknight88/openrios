# 文档到 RTL 的生成流程 (RTL_gen_workflow.md)

**前提：输入文档集已经确认闭合。** 本流程只在闭合判定成立之后启动。文档的完备性在本流程内是**既定事实**——不再验、不再补、不再回填。本文没有「发现文档缺口 → 回填 → 重跑闭合门」这条回路；真撞上文档不足以生成，那是**异常**，见 §5.2。

**输入只有三类设计源**：`isa_card/`、`registry/architecture.md`、`module/**/*.md`。**除此之外一概不读**——闭合门的报告、派生物、规范条文、检查工具，与 RTL 生成无关。

**边界**：上游是闭合流程（文档完备性归它），下游是验证流程（行为正确性归它）。中间这一段——把已确定的设计事实翻译成合法的 RTL——才是本文。

**终点**：一份 lint 干净、端口与文档逐条对得上、连接齐备的全设计 RTL。**行为对不对不在本文。**

---

## 1. 输入

### 1.1 三类设计源（只读，全部输入）

| 输入 | 本流程从中取什么 |
| :--- | :--- |
| `isa_card/**/*.yaml` | **编码**：`decode.encoding.match` 的位图案。**运算语义**：`calculate` 给表达式与位宽，`update` 给写回与 next_pc，`memory` 给访存请求形态，`dynamic_check` / `outcome` 给非法条件与异常 |
| `registry/architecture.md` | `层级` 给模块树与实例；`通道` 给执行单元、单元行括号里的**分类集合名**、以及该单元**认领哪些指令**；`连接` 给绑定、广播、`field_map` / `subset`；`参数` 给跨模块位宽与上界。**子操作编码布局也在这里声明**——位图案怎么折成子操作值是设计取舍，不是流程 |
| `module/**/*.md` | 五个根章节：`Submodule`、`FSM`、`Data structure`、`Internal Connections`、`Interface`。**跨模块结构类型在首次引入处定义**，schema 由此收拢 |

### 1.2 不读什么

**闭合门的派生物一律不读。** 报告、`schema` / `hierarchy` / `integration-layer` / `top-contract` 的派生副本、各种 trace——它们全是上面三类源的投影。生成器回读派生物就是拿派生物当 oracle，之后所有「对得上」都不再有意义。凡这些文件里有的，本流程一律从三类源自己算。

**既有 RTL 一律不读。** 无参照 RTL 是本流程的前提；既有 RTL 至多是可选 oracle，任何阶段都不得把它当判据、当输入、当参考。

**ISA 手册一律不读。** 卡已由人对 Sail 与 UDB 逐条核实，运算语义在卡里且机器可读。生成器按卡实现，不得回到手册、Sail 或 UDB 取任何事实。卡不足以确定实现是异常，见 §5.2。

**规范条文与检查工具不是本流程的输入。** 三类源怎么写、闭合怎么判，由闭合流程的规范约束，本文不复述也不引用；本流程只读那三类源已经写成的内容。

### 1.3 外部工具

**Verilator**：静态检查。命令见 §4.5。

---

## 2. 阶段

```text
闭合已确认 ─▶ 1 package ─▶ 2 模块本体 ─▶ 3 顶层集成 ─▶ 4 全设计静态检查 ─▶ 交验证流程
                  │             │              │                │
             可编译且齐全  lint 0 + 端口对账 0   无悬空/多驱动    0 error + warning 归类
```

| 阶段 | 名称 | 源 | Gate | 不过退到 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | package 生成 | 卡 + 架构 + module | 三个 package 齐全、可编译、顺序正确，值可重算并逐条相等 | 查生成器 |
| 2 | 模块本体 | module + 卡 + 架构 | 每份 lint 0 error + 端口幂等对账 0 + 台账归类完 | 查生成器；或 `GD-规` 停 |
| 3 | 顶层集成 | 架构 + 顶层 module | lint 0 error，无未驱动、无多驱动、无悬空 | 阶段 2，或查生成器 |
| 4 | 全设计静态检查 | 生成物 | 0 error，warning 逐条有结论 | 产生该 warning 的阶段 |

**每阶段必须能失败。** Gate 判定只取 `PASS` / `FAIL` 两值，不设「基本通过」。

**四个 Gate 的失败归因只有两类**：生成器没照规则做，或规则没规定这种形态。没有第三类——第三类是异常。

---

### 2.1 阶段 1：package 生成

**三个 package 全部从三类源现算。** 不与任何既有 package 比对，也不抄任何编码登记——那种登记是卡的投影，回读即自证。

| package | 源 | 生成什么 |
| :--- | :--- | :--- |
| `isa_pkg` · 编码 | 每张卡的 `decode.encoding.match` + `架构` 声明的子操作编码布局 | 按该布局把位图案折成一个子操作常量 |
| `isa_pkg` · 分类集合 | `架构 · 通道` 单元行的 `单元 (集合名)` 给名字；该单元认领的指令清单给成员 | 每个集合一个 `function automatic logic`，成员表即 `inside {…}` |
| `schema_pkg` | module 文档里首次引入处的类型定义 | 每个跨模块类型一个 `typedef struct packed`；**字段书写顺序即 packed 位布局，首字段在最高位** |
| `params_pkg` | `架构 · 参数` | 每条 `NAME = 值` 一个 localparam；**派生关系按原式生成，不展开成常数**；为空也生成 |

- **编译顺序**：`isa_pkg → schema_pkg → params_pkg`，写入 `pkg/ORDER`。
- **Gate**：
  1. 三个 package 齐全、可编译、顺序正确。
  2. 每个跨模块类型有对应 `typedef`，字段位宽之和等于声明总位宽。
  3. **每个子操作常量可由卡的位图案按架构声明的布局重新算出并相等**，且全表无重码。
  4. 每个分类集合有对应函数，成员与架构的认领清单逐个相等。
---

### 2.2 阶段 2：模块本体

**一次一个模块，生成完即 lint、即对账，两样都过才进下一个。**

- **顺序**：按 `架构 · 层级` 由叶子向 root。经验序：零 state 叶子 → 有 FSM 的叶子 → 含握手与优先级的模块 → 执行单元 → root。private 块单独成文件，由父模块实例化。
- **输入**：三个 package + 一份 module 文档（生成 private 块时加其父模块文档）+ `架构 · 通道`（取该模块认领的指令）。
- **动作**：按五个根章节逐节生成。

| 文档章节 | 生成物 |
| :--- | :--- |
| `Submodule` | 子模块实例化语句 |
| `FSM` / `State`、`State Transition` | 状态寄存器与时序逻辑 |
| `FSM` / `Detailed Condition Description` | 条件的组合逻辑（公式树逐层展开） |
| `Data structure` / `State`、`Header`、`Payload` | 存储声明与更新逻辑 |
| `Internal Connections` | 模块内连线 |
| `Interface` | 端口列表，四项机器可读信息从条目行提取（见下） |
| `Interface Timing` | 断言（生成形式见 §4.4） |

**Interface 条目行的四项**，都在条目行里，不另找别处：

```text
类型      payload=`名字_t`，或 Event 的 - Payload：`名字_t`
位宽      标量写 N bit
索引集合  `符号∈{值,值}`
固定归属  括号里写 域=值
```

- **运算语义取自卡，不取自 module 文档。** module 文档只写状态、事件、表达式、schema、位宽、时序与更新规则，**逐条指令算什么不在其中**。生成一个执行单元时：
  1. 由 `架构 · 通道` 取该单元认领的指令清单；
  2. 逐条指令读其卡的 `calculate`、`update`、`memory`、`dynamic_check`、`outcome`；
  3. 按子操作常量分支实现。分支取值用阶段 1 生成的 `isa_pkg` 常量，**不得**另行拼编码。

- **四条取值规则。** 文档已闭合，这四样必然写着；**读不到即异常**（§5.2），不是记个占位继续往下的理由。
  1. **复位值**：优先取 `reset` Event 的 State update；零 state 模块取 `Interface Timing` 第 2 条。
  2. **多 Event 写同一寄存器的优先级**：取文档明写的优先级行，或 `Constraint` 行里明写的「优先于」。
  3. **Transaction 的 ready 指名**：取本模块文档指名的那个 Out Static Info 端点。
  4. **译码谓词**：由卡的编码与语义槽算出，与阶段 1 的 `isa_pkg` 同源同法。

- **Gate**（四条全过）：
  1. **lint 0 error**，每条 warning 有归因结论。
  2. **端口幂等对账为 0**：从生成的 `.sv` 反推端口，与该模块 `Interface` 章展开的叶子逐条配对。方向、位宽、索引基数是硬约束，名字只做消歧。
  3. 本模块每条台账条目有分类与去向。
  4. **人工审读至少一个 `always_ff` 块**。这是对「语法合法但语义错」那类盲区的权宜措施，**不是**语义正确的判据。
- **失败归因**：端口名、位宽、方向不符 → 生成器；形态无规则可依 → `GD-规` 停。
---

### 2.3 阶段 3：顶层集成

- **输入**：全部 module 的 `.sv`、`架构 · 层级`、`架构 · 连接`、顶层 module 文档。
- **动作**：
  1. **实例化**：按 `架构 · 层级` 逐个实例化。**一份文档多个实例时各自成一个实例**，端点按实例限定。
  2. **内部连线**：`架构 · 连接` 每条绑定生成一条 wire 连接。**广播用 `*.端点名` 通配并紧随一条接收清单，先按清单展开成 N 条，再逐条生成。**
  3. **字段改名与部分接收**：`field_map` / `subset` 是**绑定的属性，不是端点的属性**，写在连接行上，按该行生成字段级连接，不改端点声明。
  4. **顶层边界**：`clk`、`rst_n` 与所有对外接口在顶层文档的 `Interface` 归档，据此生成顶层端口列表。
  5. **private 块**：按 `架构 · 层级` 标为 private 的归其 parent，以 `<parent>__<block>.sv` 产出并由 parent 实例化，**不外泄为顶层端口**。
  6. **边界对端契约模块**：描述文档集**之外**对端的模块**不实例化、不生成设计**，只生成验证桩。其端点与顶层边界端口逐个反向镜像（本模块的 In 对顶层的 Out），名字、kind 与 schema 三项一致。设计里没有这类模块时本条不触发。
- **Gate**：lint 0 error；**无未驱动、无多驱动、无悬空**。
- **失败归因**：模块侧端口不符 → 回阶段 2；连线漏生成、实例漏生成 → 生成器。

---

### 2.4 阶段 4：全设计静态检查

- **输入**：完成顶层集成的全设计 RTL。
- **动作**：以 root 为顶层跑一次全设计 lint，检查位宽、锁存器、组合环、多驱动、未驱动、未使用信号。
- **Gate**：**0 error**；**warning 逐条有结论**——定位到归因，或在台账里具名豁免。
- **失败归因**：退到产生该 error / warning 的阶段。

## 3. 输出

| 产物 | 说明 |
| :--- | :--- |
| `pkg/*.sv` + `pkg/ORDER` | 三个 package 及其编译顺序 |
| `<module>.sv` | 每份 public module 一个文件 |
| `<parent>__<block>.sv` | 每个 private 块一个文件，由父模块实例化 |

## 4. 生成器的约束

### 4.1 不得引入文档没有的东西

生成器不得为通过 lint 而增加端口、寄存器、状态、默认值或优先级，**也不得为此修改文档**。凡需要而文档没有的，走 §5.2。

### 4.2 留痕

- 每个 `always` / `assign` 块前注释 `// doc: <文件>#<章节>#<条目>`。公式树子项标到父条目，`见第 N 条` 标被引条目。
- 运算语义处注释 `// card: <助记符> · <槽>`，例如 `// card: ADD · calculate`。
- `TRACE.md` **反向**列出文档每条条目对应的 RTL 行；**没有对应的条目单列**——那是生成器漏，不是文档漏。
---

## 5. 失败与异常

### 5.1 流程内的失败（两类）

| 根因 | 判据 | 动作 | 重跑起点 |
| :--- | :--- | :--- | :--- |
| **生成器没照规则做** | 规则写了，生成物不符 | 就地修生成器 | 产生问题的那个阶段 |
| **规则没写 / 写错** | 文档写全了，但本文与生成规则都没规定这种形态该翻成什么 | 记下错误，**停在该处**；改生成规则下一版 | 该阶段 |

**这两类都不碰设计源。** 本流程内任何时候都不修改 `isa_card/`、`architecture.md` 或 `module/**/*.md`。

---

## 6. 交付与边界

阶段 4 通过时交付：

```text
pkg/*.sv + pkg/ORDER
<module>.sv · <parent>__<block>.sv · 顶层
逐模块与全设计 lint 报告
端口幂等对账报告
```

**阶段 4 通过只说明生成物合法，不说明它对。** lint 过、端口对账过、人工审读过，三样加起来都不能判定行为正确——语法与连接都合法而语义错误的生成物，本流程内没有任何一道门能抓。**判断「做出来对不对」由验证流程承担**：仿真、参考模型比对、回归，以及由此产生的差异归属与回流。那条流程的输入就是上面这份交付物，它的定义、环境、激励与判据不在本文。
